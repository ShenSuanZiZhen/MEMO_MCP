# 模块化 MCP 构建套件全局开发约束

> 本文件适用于所有 WP。任何工作包都不能放宽这些约束；冲突时停止并请求技术负责人决定。

## 1. 产品边界

1. P0 是只读 MCP 构建与运营平台，不实现写数据库、写外部 API、删除外部数据、资金交易、原文件下载、整篇读取、整库导出、任意 SQL、用户脚本或用户容器。
2. Prompt 只能编排已经授权的 Tool/Resource，不能创造新权限。
3. 平台身份、策略、配额、输出保护和审计层始终启用，UI 和高级配置均不能关闭。
4. 不实现当前工作包未明确要求的 P1 能力，不为“以后可能需要”预建业务功能。

## 2. 架构不变量

1. P0 使用模块化单体控制面、独立 MCP Gateway、持久化 Worker；未经 ADR 不拆新微服务。
2. `Service Definition` 是预览、测试、审核和运行的唯一事实。
3. Draft 可编辑并使用 revision/ETag；Candidate 和 Published Version 不可变。
4. 相同输入必须产生相同 canonical Definition 和 SHA-256 digest。
5. 运行制品摘要必须与批准 Definition 摘要相同，否则禁止开放流量。
6. `domain` 不导入 Web、数据库、Temporal、OPA、Redis、OpenSearch 或云 SDK；基础设施实现领域端口。
7. 依赖方向为 `apps -> application/use-case -> domain`，禁止循环依赖和跨层快捷访问。

## 3. 数据与租户约束

1. 每个业务请求从已验证身份构造 `ActorContext`；客户端传入的 workspace/project 不能作为可信身份。
2. 所有租户数据显式携带 workspace/project/environment；数据库 RLS 作为第二道防线。
3. 对象存储、搜索索引、Redis key 和 telemetry 均包含隔离维度。
4. 无权和不存在对外返回同类结果，不能泄露资源是否存在。
5. DataVersion 不可变；已发布版本只引用完成且确认的数据版本。
6. 生产数据和真实 Secret 不得进入本地、测试 fixture、日志或提交。

## 4. 安全约束

1. 每次 MCP 初始化、发现、列举、读取和调用均执行认证、策略、配额和范围检查。
2. 策略、配额或受保护依赖无法确认时关闭式拒绝。
3. Secret 只展示一次；库中保存密文或不可逆哈希及摘要，禁止正文、Secret、完整 URL 参数、查询文本和堆栈进入日志/事件/报告。
4. 文件先隔离和扫描；解析器无默认网络、非 root、只读根文件系统并受 CPU/内存/时间/展开大小限制。
5. HTTP 连接器阻断私网、loopback、link-local、metadata、DNS 重绑定和重定向绕过。
6. 数据库连接器只接受允许表/视图/字段和参数化过滤，不接受 SQL 文本。
7. 生产模块必须精确版本、已审核、摘要锁定并验证签名。

## 5. 一致性与可靠性

1. 所有创建、重试、部署、计量写接口使用幂等键；同键异参拒绝。
2. 长任务持久化，Activity 可重试，业务结果通过唯一约束恰好一次生效。
3. 状态写入和 outbox 同事务；消费者去重。
4. 数据库迁移使用 expand/migrate/contract，不修改已合并迁移；破坏性迁移必须单独评审。
5. Redis 和 OpenSearch 不是唯一事实；必须可从 PostgreSQL/对象制品重建。

## 6. 范围控制

1. 只修改当前工作包“允许修改”的目录；发现必须跨界时停止并说明原因。
2. 不顺手升级依赖、不全仓格式化、不重命名无关 API、不清理无关 TODO。
3. 默认单包有效代码 200～1200 行、5～30 个相关文件；明显超过时先拆分或请求确认。
4. 新抽象必须至少有当前包内两个真实调用者；否则使用最简单实现。
5. 只为验收用例实现必要行为，不增加隐藏开关或未评审扩展点。

## 7. 实现与测试规范

1. TypeScript strict；跨边界输入用已冻结 schema 验证，禁止仅靠类型断言。
2. 时间使用 UTC，ID 是 opaque string；列表使用稳定 cursor。
3. 错误使用统一错误码和信封，不返回内部堆栈。
4. 测试使用合成数据；权限、安全、幂等和不可变规则必须有负例。
5. 每包先运行目标包测试，再运行 `pnpm verify:affected`；共享契约、迁移或里程碑包运行 `pnpm verify`。
6. 不通过降低覆盖率、跳过测试、扩大超时、删除断言或 mock 掉核心规则来获得绿灯。

## 8. 开始与停止条件

开始前必须：

- 阅读本文件、当前 WP、列出的 PRD/方案章节及所有直接依赖 evidence；
- 运行 `./scripts/check-work-package-ready.sh <WP-ID>`；
- 确认工作树中已有变更并识别其归属，不覆盖用户或其他 WP 的修改；
- 记录基线和实际可用命令。

以下情况必须停止：

- 直接依赖没有 `status: PASS`；
- 需要破坏已冻结契约或 Definition canonicalization；
- 需要生产 Secret、真实客户数据或外部写操作；
- 需要放宽安全/租户/关闭式拒绝规则；
- 必须修改禁止目录或超出单包规模；
- 测试暴露与当前目标无关的既有故障，且无法隔离。

## 9. 衔接与完成

1. 新增/修改契约、migration、事件、环境变量、feature flag、端口或运行命令必须写入 evidence。
2. 下游只依赖公开接口和 evidence，不依赖未提交临时实现或测试内部细节。
3. 只有验收命令全部通过并创建 `docs/work-package-evidence/<ID>.md`，状态才可写 `PASS`。
4. 人工门禁包由 Codex 标记 `IMPLEMENTED_AWAITING_REVIEW`，评审通过后才改为 `PASS`。
5. 最终回复必须包含结果、文件、验证、约束核对、风险和下一可执行 WP；禁止只说“已完成”。
